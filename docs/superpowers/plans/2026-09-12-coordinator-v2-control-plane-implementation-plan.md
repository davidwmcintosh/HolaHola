# Coordinator V2 Control Plane Implementation Plan

**Date:** September 12, 2026
**Design:** `docs/superpowers/specs/2026-09-12-coordinator-v2-control-plane-design.md`

## Goal

Replace the brittle one-shot Gate 3 operating model with a server-owned,
policy-bound Coordinator V2 lifecycle. The first host is a thin Windows agent
using PowerShell 5.1 and DPAPI `CurrentUser`; the protocol remains host-neutral
and provider-neutral.

The finished operator flow is one `Invoke-HolaCoordinator` command. PostgreSQL
owns policy, session, attempt, lease, evidence, retry, fallback, and terminal
state. Transport failures resume without regenerating logical task authority.
Intentional provider retries and fallbacks use fresh attempts and fresh
one-time authority.

## Implementation constraints

- PostgreSQL remains the canonical authority and evidence store.
- GitHub repository identity, starting commit, and artifact digests remain
  immutable source provenance.
- Luca remains provider-neutral. Provider, model, adapter, runtime, and host
  labels are provenance only.
- Founder approval applies to immutable policy versions.
- Authorized operators launch bounded sessions under approved policies.
- Provider fallback follows only the approved policy order and failure classes.
- Provider output never grants execution authority.
- A non-terminal attempt may resume only for transport recovery.
- A logical retry or provider switch always creates a fresh attempt and fresh
  one-time authority.
- Failed or completed authority artifacts are never reused.
- Historical Gate 3 rows remain immutable and queryable.
- Preflight is read-only.
- Local preparation is staged and atomically promoted.
- Windows uses native PowerShell 5.1 and DPAPI `CurrentUser`.
- No code, test, runbook, or product statement may claim protection against
  malicious software running as the same Windows user.
- Task 1449 remains cancelled.
- Alden-owned task 1450 is not modified, duplicated, or inferred to be locally
  owned.
- No real Windows authority is created until the implementation and hermetic
  proof gates preceding real-Windows acceptance have passed.
- Schema work follows the HolaHola schema-change procedure: update
  `shared/schema.ts`, generate and review a migration, prove it on a Neon
  branch, then apply the reviewed migration.
- Database-writing regression tests use only a verified disposable database.

### Tables

Add narrowly scoped tables for:

- host enrollments and host lifecycle;
- trust-policy identities;
- immutable trust-policy versions;
- founder policy decisions;
- operator policy grants;
- bounded sessions;
- immutable session transition events;
- attempts;
- immutable attempt transition events;
- durable transport leases;
- cleanup obligations and acknowledgements.

### Required database constraints

1. Policy version content is immutable after creation.
2. A policy version has one canonical digest and an explicit approval state.
3. A session references exactly one policy version and one enrolled host.
4. Session task, repository, starting commit, host, expiration, and budgets are
   non-null and bounded.
5. Session terminal state and terminal timestamp agree.
6. Attempt ordinals are unique within a session.
7. Provider ordinals are unique within a session and provider.
8. Attempt terminal state and terminal timestamp agree.
9. At most one accepted completion exists per session.
10. Transport lease holder, epoch, expiry, and lifecycle timestamps agree.
11. Only one current transport lease exists per session.
12. Cleanup obligations are unique by session and cleanup kind.
13. Historical evidence references use restrictive deletion behavior.
14. V2 tables do not cascade-delete existing coordination evidence.

### Tests

- Reject invalid policy lifecycle combinations.
- Reject mutable replacement of an approved policy version.
- Reject invalid session and attempt terminal-state combinations.
- Reject duplicate attempt ordinals.
- Reject a second accepted completion.
- Reject duplicate active transport leases.
- Prove historical evidence survives V2 row cleanup attempts.
- Prove the migration starts from the canonical ledger and applies on a fresh
  Neon branch.

### Gate

- Generated SQL is reviewed line by line.
- The migration passes on a Neon branch.
- The disposable-database schema suite passes.

## Completion criteria

The implementation is complete only when:

- both real-Windows acceptance sessions pass;
- the operator used one command and copied no internal identifiers;
- transport interruption resumed without regenerated logical authority;
- provider failures followed the approved retry and fallback policy;
- every logical retry used fresh attempt authority;
- PostgreSQL contains complete immutable evidence;
- GitHub and deployment provenance are exact;
- terminal cleanup left no live session credential, claim, or lease;
- all required validation and system-health checks pass;
- Alden's Anthropic and Gemini engines give unconditional approval;
- the manual Gate 3 operating path is retired;
- task 1449 remains cancelled;
- Alden-owned task 1450 remains untouched;
- documentation states the same-Windows-user limitation without qualification.
