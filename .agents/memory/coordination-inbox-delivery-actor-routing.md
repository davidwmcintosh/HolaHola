`shouldCreateInboxDelivery()` in `server/services/coordination-ledger-service.ts` gates delivery creation only on the RECIPIENT being `luca-replit` or `luca-claude-code`, but `inboxActors()` in `server/services/coordination-delivery-worker.ts` additionally requires the ORIGIN to be the *other* one of that same pair -- it recognizes exactly two routes (`luca-replit -> luca-claude-code` and the reverse) and nothing else. Any coordination thread whose origin is a different actor (alden, luca-gemini-code, luca-antigravity, luca-holahola, david, ...) sending to either Luca hat passes the first gate, creates a `coordination_adapter_deliveries` row in `pending` state, and then permanently fails in the worker with `agent_notes cannot project <origin> -> <target>` after its retry budget (3 attempts) is exhausted -- landing in `status: 'failed'` with no further silent retries.

**Why:** the underlying `coordination_threads`/`coordination_events` ledger write itself always succeeds regardless of actor -- that is the authoritative record and is actor-agnostic. Only the secondary UI-facing mirror into `agent_notes` (what actually shows up as an unread inbox item to a Luca hat) is narrowly scoped to the two-Luca-hat conversation this adapter was originally built for. A caller checking only `SharedSpecNotificationSink.deliver()`'s own return value (`{state: "delivered"}`, which reflects the coordination-thread write succeeding) will believe the notification reached its recipient's inbox when it never did. Confirmed for real: a `review_decided` notification with `initiatingActorId: "alden"` delivered its canonical coordination thread successfully but never appeared as an `agent_notes` inbox item for luca-replit.

**How to apply:** don't trust a notification sink's "delivered" state as proof an inbox item was created for any origin actor other than the two Luca hats. To check whether a specific coordination thread's inbox mirror actually landed, query `coordination_adapter_deliveries` (join `event_id` -> `coordination_events.thread_id`) for that thread and check `status`/`last_error`, not just the thread's own existence. Alden already has a separate, working path into a Luca hat's inbox: an `@agent` mention in Team Room auto-creates an `agent_notes` row (see team-room-presence.md) -- that path is unaffected by this gap. Extending `inboxActors()` to support more origin actors is a routing/trust-boundary decision (who is allowed to write into whose inbox), not a bug fix to make unilaterally -- surface it for a decision rather than patching the whitelist ad hoc.


**Update, Sep 29 2026:** fixed. `inboxActors()` in `coordination-delivery-worker.ts` now accepts any `CoordinationActorId` as the origin (mapped through the same `agentNotesIdentity()` convention: `luca-replit` -> `'agent'`, everyone else uses their literal actor id) as long as the target is `luca-replit` or `luca-claude-code` and origin != target. Verified for real against the stuck historical delivery (not just by inspection): forced a retry of the `alden -> luca-replit` delivery row that had been failing since before the fix, and it produced exactly one new `agent_notes` row (`from_agent: 'alden'`, `to_agent: 'agent'`) with the delivery flipping to `status: 'delivered'`.

The recipient-side restriction is untouched and still matters: `shouldCreateInboxDelivery()` in `coordination-ledger-service.ts` only creates a delivery row at all when the *recipient* is `luca-replit` or `luca-claude-code` -- no other actor (alden, david, daniela, other Luca runtimes) has an `agent_notes` inbox to deliver into. So `SharedSpecNotificationSink.deliver()` (or any other caller of `createCoordinationThread`) returning `{state: "delivered"}` still only proves the canonical coordination-thread/event write succeeded, never that an inbox item was created, whenever the recipient isn't one of those two actors. The original "how to apply" guidance above (query `coordination_adapter_deliveries` to check the real inbox-mirror outcome) still stands for that case.
