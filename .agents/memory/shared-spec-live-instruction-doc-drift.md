Some files under `docs/` that look like plain git-tracked markdown are actually governed by the shared-spec system as `liveInstructionDocument: true` records (confirmed for `docs/coordination-clients.md` and `docs/shared-agent-instructions.md`, seeded by `server/scripts/seed-live-instruction-documents.ts`). Each has a `shared_spec_documents` row with its own `current_revision_id` pointing at a `shared_spec_revisions` row holding its own copy of the markdown. A plain `Edit`/`WriteFile` on the git file changes only the working tree -- it does not touch that DB row, so the DB's "current" content silently drifts out of sync with the real file.

**Why:** `syncLiveInstructionDocument` (server/routes/shared-spec-routes.ts) only fires as a side effect of approving a review on that document (`decision === "approve"`), and only then does it write the approved revision's markdown back over the working-tree file. There is no scheduled or startup-triggered sync -- confirmed by grepping for callers of that function and of `GitWorkingTreeLiveSyncProvider`. So a raw git edit is not at *immediate* risk, but it creates a live landmine: if a future agent later builds a new revision from the stale DB content (e.g. via `shared-spec-cli.ts show`/`export` rather than reading the live git file) and that revision gets approved, the approval silently overwrites the working tree back to that stale lineage -- erasing the untracked git edit with no error.

**How to apply:** before or immediately after directly editing one of these files, check whether it is shared-spec-governed (`select * from shared_spec_documents where canonical_path = '<path>'`, or check `server/scripts/seed-live-instruction-documents.ts`'s target list). If it is, close the gap yourself: append a matching revision so the DB stops diverging, in-process (mirroring `seed-live-instruction-documents.ts`'s pattern -- import `SharedSpecCore` + `PostgresSharedSpecRepository`, call `core.appendRevision({actorId: "<your hat>"}, {documentId, baseRevisionId: <current>, markdown: <the file's real current content>, idempotencyKey})`), not a raw SQL write against `shared_spec_revisions` (bypasses content-hash/idempotency invariants the service enforces). This leaves the document honestly in `state: "draft"` -- accurate, since the new content hasn't been independently reviewed -- rather than a stale `"approved"` state that no longer matches the file. Getting a real review/approval requires a genuinely different actor's credential; do not fabricate one just to flip the state back to approved.
