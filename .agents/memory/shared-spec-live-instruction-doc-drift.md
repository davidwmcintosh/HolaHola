Some files under `docs/` that look like plain git-tracked markdown are actually governed by the shared-spec system as `liveInstructionDocument: true` records (confirmed for `docs/coordination-clients.md` and `docs/shared-agent-instructions.md`, seeded by `server/scripts/seed-live-instruction-documents.ts`). Each has a `shared_spec_documents` row with its own `current_revision_id` pointing at a `shared_spec_revisions` row holding its own copy of the markdown. A plain `Edit`/`WriteFile` on the git file changes only the working tree -- it does not touch that DB row, so the DB's "current" content silently drifts out of sync with the real file.

**Why:** `syncLiveInstructionDocument` (server/routes/shared-spec-routes.ts) only fires as a side effect of approving a review on that document (`decision === "approve"`), and only then does it write the approved revision's markdown back over the working-tree file. There is no scheduled or startup-triggered sync -- confirmed by grepping for callers of that function and of `GitWorkingTreeLiveSyncProvider`. So a raw git edit is not at *immediate* risk, but it creates a live landmine: if a future agent later builds a new revision from the stale DB content (e.g. via `shared-spec-cli.ts show`/`export` rather than reading the live git file) and that revision gets approved, the approval silently overwrites the working tree back to that stale lineage -- erasing the untracked git edit with no error.

**How to apply:** before or immediately after directly editing one of these files, check whether it is shared-spec-governed (`select * from shared_spec_documents where canonical_path = '<path>'`, or check `server/scripts/seed-live-instruction-documents.ts`'s target list). If it is, close the gap yourself: append a matching revision so the DB stops diverging, in-process (mirroring `seed-live-instruction-documents.ts`'s pattern -- import `SharedSpecCore` + `PostgresSharedSpecRepository`, call `core.appendRevision({actorId: "<your hat>"}, {documentId, baseRevisionId: <current>, markdown: <the file's real current content>, idempotencyKey})`), not a raw SQL write against `shared_spec_revisions` (bypasses content-hash/idempotency invariants the service enforces). This leaves the document honestly in `state: "draft"` -- accurate, since the new content hasn't been independently reviewed -- rather than a stale `"approved"` state that no longer matches the file. Getting a real review/approval requires a genuinely different actor's credential; do not fabricate one just to flip the state back to approved.

**Refinement (2026-09-28):** the above covers *capturing* pre-existing status-quo content (drift reconciliation). When the new content is genuinely new authored material rather than a capture of what was already true, also call `core.markRevisionReady(actor, { documentId, revisionId, idempotencyKey })` right after `appendRevision` -- this moves the document to `ready_for_review` and creates a real, claimable `shared_spec_reviews` row (`state: "pending"`), which is more honest and more discoverable than leaving it in bare `draft`: a draft document has no pending-review row at all, so nothing signals to a reviewer that it needs attention. `ready_for_review` is what a genuine reviewer's queue (`idx_shared_spec_reviews_pending`) actually surfaces. Still never self-approve -- claiming and approving requires a different actor's credential, via `server/scripts/shared-spec-cli.ts claim`/`approve`.


**Refinement (2026-09-29): a decide-time bypass drifts the file even though the DB says approved.** A second, opposite-direction drift from the one above: calling `SharedSpecCore.approveReview()`/`rejectReview()` directly from a new in-process caller (bypassing the HTTP route in `server/routes/shared-spec-routes.ts`) changes DB state correctly but silently skips both the `review_decided` notification and, for a `liveInstructionDocument`, the git working-tree sync -- `SharedSpecCore` itself never touches notifications or git by design (see its own top-of-file doc comment). Confirmed for real: Alden approved review `613dc7f4`/document `b9c22d87` (`docs/shared-agent-instructions.md`) through a first version of his decide tool that called `core.approveReview` directly; the document row read `state="approved"` while the on-disk file's md5 still matched the prior revision, with `git log` showing no new commit and no notification delivered.

**Why:** the route's approve/reject handler was the only place that chained `core.approveReview` -> `deliver(review_decided)` -> `syncLiveInstructionDocument(...)` -- that sequence lived as a private closure inline in the route, not exported, so it was invisible to anyone writing a second entry point who only looked at `SharedSpecCore`'s own public methods.

**How to apply:** the sequence is now extracted as `decideSharedSpecReviewWithEffects` (`server/services/shared-spec-review-decision.ts`), exported and used by both the HTTP route and `alden-shared-spec-review.ts`. Any new entry point that decides a review must call this function, never `core.approveReview`/`rejectReview` directly. It must also be given the *same* process-wide `liveSync`/`notifications` singletons (`getHolaHolaSharedSpecLiveSync`/`getHolaHolaSharedSpecNotificationSink` in `server/adapters/hola-hola-shared-spec-bootstrap.ts`), not freshly constructed instances -- `GitWorkingTreeLiveSyncProvider` serializes concurrent syncs to the same gitPath only within one instance, so a second instance built elsewhere would not be serialized against the route's instance. To retroactively fix a document already left in this stale-approved state, `POST /api/shared-spec/documents/:id/resync` (any authenticated actor, no reviewer capability required) re-applies the current approved revision to disk without re-deciding the review.
