A plain text/regex-based guard script that hunts for a call-pattern shape (e.g. `.approveReview(`) can match its own source: a doc comment explaining what the pattern looks like, or a `--self-check`'s fixture-file-content string literals, both contain the literal pattern without being a real call site. Confirmed while writing a bypass guard for `shared-spec-review-decision.ts`'s `approveReview`/`rejectReview` wrapper: the real-check scan failed on first run, flagging the guard script's own header comment and its self-check's embedded fixture strings -- not any actual violation elsewhere in the codebase.

**Why:** a naive per-line regex scan (the same style already used by `test-cli-entrypoint-guard-pattern.ts` and the image-upload scanners) has no concept of comments or string literals -- any file containing the pattern as literal text, including the guard's own source, matches identically to a real call site.

**How to apply:** when a new text-scanning guard's own file will necessarily contain the literal pattern it hunts for (in its header/doc comment explaining the pattern, or in `--self-check` fixture content), exempt the guard's own path from the scan in addition to any legitimate production exemption. Compute that self-exemption from `__filename` rather than hand-copying the path, so a rename can't leave it stale. Re-run the real check (not just `--self-check`) before trusting a "0 violations" result -- the self-check alone will not surface this, since it scans a throwaway sandbox, not the guard's own real file.
