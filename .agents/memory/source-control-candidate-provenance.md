`status.state === 'ready_to_promote'` does not by itself mean a human deliberately ran `prepare` against that commit. `SourceControlService.syncLocked()`'s auto-merge-and-revalidate branch (GitHub ahead of Replit, clean fast-forward) also produces `ready_to_promote`, with the same shape -- correct candidateSha, unexpired, a structurally valid manifest -- as an explicit `prepare` run. A `candidateSource` field on the status record is what tells them apart: `undefined` means an explicit `prepare` produced it, `'auto_sync'` means the scheduler did.

**Why this matters:** Replit's Publish button always builds whatever commit is on HEAD, not a specific validated SHA. Before this field existed, an auto-promoted commit landing on HEAD between a real `prepare` and the user clicking Publish let Publish silently ship code nobody explicitly reviewed -- confirmed in practice when an auto-promoted commit superseded a validated candidate within minutes and the next Publish deployed the unvalidated one.

**How to apply:** `recordLocked()` refuses (fails closed, points at `npm run source-control:prepare`) whenever `candidateSource === 'auto_sync'`, even if every other check (matching sha, unexpired, valid manifest) passes -- do not weaken or bypass this check just to let an auto-promoted candidate through. Before telling anyone it is safe to publish, run `npm run source-control:drift`, which live-checks HEAD against the last `prepare`-validated candidate; `status` alone only reports the last known state without re-checking HEAD. Every git call in this service, even a local no-network `rev-parse HEAD`, goes through `withGithubAppAuth` and mints a fresh token first, so `drift` is not instant the way the pure-file-read `status` is -- that is why it stays a separate opt-in action instead of folding into `status`.
