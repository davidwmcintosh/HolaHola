A static-analysis script that resolves "what does this identifier's value trace back to" must walk the AST's real lexical scope chain (innermost enclosing block/function/catch/for-loop, outward) and stop at the first scope that actually declares the name -- never fall back to a whole-file "first declaration with this name anywhere" search.

**Why:** a whole-file search finds the first same-named `const`/`let`/`var` textually, regardless of which function or block it lives in. When a script has an inner function parameter or local named the same as an unrelated outer/sibling-scope variable (a very common pattern: `path`, `out`, `dir`, `tmpCommit` reused across several small helper functions), the whole-file search silently binds to the wrong declaration. This can accidentally produce a safe-looking resolved value (masking a real violation) or an unresolvable one (raising false positives) purely by textual luck, not by correct data flow. It surfaced as a real, reviewer-flagged bug in the server/scripts source-mutation-write scanner: several genuinely-safe sandboxed writes were silently validated via the WRONG same-named declaration until scope-aware resolution was added.

**How to apply:** when writing or reviewing any of this project's `scan-*`/`test-*-ci-check` static-analysis guards (the family of scripts that parse other scripts' ASTs to prove a pattern is or isn't present), implement variable-origin tracing as: define real scope-boundary node kinds (SourceFile, Block, CaseBlock, function/arrow/method bodies, CatchClause, for/for-in/for-of), collect only the declarations introduced directly by one boundary at a time, and walk `node.parent` outward one boundary at a time -- a function parameter or catch binding with no initializer must resolve as "found in this scope but unresolvable," never fall through to an outer same-named declaration. Fail closed (treat as a violation) on true dead ends, not open.
