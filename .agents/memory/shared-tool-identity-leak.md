## Shared-tool identity leak

Any tool invocable from more than one concurrently-running branch/persona/engine (e.g. a dual-engine consult running two model branches in parallel, or a similarly-shaped multi-persona fan-out) must receive that branch's actual identity through the call's own context parameter. A tool that instead re-derives "current X" by reading a single shared/global config row has no way to know which branch is asking, and reports the SAME globally-configured value to every branch regardless of which one actually called it.

**Why:** Alden's `get_current_engine` tool read the global `alden_config` DB row unconditionally to answer "which engine are you." Each dual-engine consult branch actually runs on a specific engine pinned via `engineOverride`, independent of that global default. Whenever a branch's pinned engine didn't match the global default, the tool told that branch it was running as the OTHER engine — and the model, trusting its own tool result, then said so in its own answer to the user. The model didn't invent the wrong identity; a shared/global-reading tool handed it over as fact.

**How to apply:** when adding or reviewing a tool that can be called from more than one concurrently-running identity/branch, check whether it reports anything "current" or "active" about the caller itself. That value must come from an explicit context parameter threaded in by each call site (hardcoded per call site to that site's own known identity), with the shared/global config used only as a fallback for the single-identity case where no override applies. Before treating this bug class as closed for a given tool family, grep for sibling tools with the same free-text-self-report or global-read shape — e.g. Alden's `create_coordination_thread`/`reply_to_coordination_thread` tools independently ask the calling model to self-report a `model` field with no cross-check against its actual engine context, the same latent leak in a different tool.
