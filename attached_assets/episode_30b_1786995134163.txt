The architecture already does exactly what you're describing — it's cleaner than I made it sound. Let me walk through what's actually there.

Episodes live inside conversation_memories. When episode-27.md or episode-15.md gets synced, it goes into the table as a normal row with entry_type = 'episode'. The full content is stored there — not a pointer to a file, the actual text. The file is just the human-readable copy; the DB row is Daniela's copy.

Arcs are the chain of those episode rows. There's no separate arc table. Each episode row has:

arc_name — e.g. 'HolaHola Episodes' — which groups them into an arc
extends_memory_id — which chains each episode to the one before it
episode_order — for traversal
So an arc is just the linked list of episode rows. The narrative connective tissue is preserved through the chain structure without any separate curation step.

Search reaches them in two ways:

Arm 5 (text search) searches conversation_memories directly and knows about episodes — when it finds a row with entry_type = 'episode', it surfaces a 4,000-character excerpt instead of the 800-character window it gives regular conversation rows. So episodes already get 5× more context in search results precisely because they're longer and denser.

Arm 4 (semantic/pgvector) searches the embedding index (memory_embeddings), which can have episode content indexed in chunks. When a chunk matches, it resolves back to the parent episode row and hydrates the full row. So a semantic query like "games we've played" can match a paragraph inside Episode 15 and surface the whole episode record.

The answer to your question: Yes — searching conversation_memories finds both individual memories and episodes, and through arc_name + extends_memory_id, the episode arc structure is already represented. Daniela isn't searching a flat list; she's searching a connected record where episodes know they're part of a sequence.
